# 맘캠(MomCam) SBC·MCU 부품 선정 보고서

- 작성자: 다혜
- 작성일: 2026-10-16
- 관련 문서: `report/hardware.md`(부품 구성), `report/inference_engine.md`(추론 엔진), `report/container.md`(SBC 컨테이너 구조)

> **문서 상태:** 맘캠 시제품과 양산 제품에 쓸 **SBC(판단 담당)와 MCU(안전 담당)를 고른 선정안**이다. 사양은 제조사 공개 자료 기준이며, 전류·속도는 시제품에서 측정해 확인한다.

## 1. 결론

| 구분 | 선택 | 맡는 일 |
|---|---|---|
| **SBC (개발·시제품)** | **Radxa ROCK 3C (RK3566, RAM 4GB)** | 영상·소리 AI 추론, 경보 판단, 앱 알림, 실시간 영상. 컨테이너로 기능을 나눠 실행 |
| **양산 칩 검증 보드** | Luckfox Pico Ultra W (RV1106G3, 256MB) | 양산용 칩에서 같은 모델이 도는지, 속도·메모리가 맞는지 확인 |
| **MCU** | **ST STM32G031K8** (개발 중에는 NUCLEO-G031K8 보드) | 경보 부저·LED·버튼, SBC 감시(하트비트), 정전 감지, SBC가 멈추면 자체 경보 |
| 양산 구성 | RV1106G3 SoC + STM32G031 | 시제품에서 검증한 구조를 한 장의 기판으로 옮김 |

**한 줄 요약:** 생각하는 일(AI)은 NPU가 있는 SBC가, 절대 멈추면 안 되는 일(경보)은 작고 단순한 MCU가 맡는다. SBC가 멈춰도 MCU가 부저를 울린다.

## 2. 왜 SBC와 MCU를 나누는가

강의의 원칙 "AI는 SBC에서, 실시간은 MCU에서"를 맘캠에 적용했다.

| | SBC (리눅스 컴퓨터) | MCU (마이크로컨트롤러) |
|---|---|---|
| 잘하는 일 | AI 추론, 영상 처리, 네트워크, 여러 프로그램 동시 실행 | 정해진 일을 정해진 시간에 확실하게, 아주 적은 전력으로 |
| 약점 | 부팅이 수십 초, 소프트웨어가 복잡해 멈출 수 있음 | 연산력이 작아 AI 영상 분석 불가 |
| 맘캠에서 맡는 일 | 자세·울음 분석, 5초 판정, 앱 알림, 영상 보기 | 부저·LED·버튼, SBC 생존 확인, 정전 감지 |

**핵심 이유:** 맘캠에서 가장 위험한 고장은 "엎드림을 감지했는데 경보가 안 울리는 것"과 "감시가 멈췄는데 보호자가 모르는 것"이다. 리눅스는 업데이트, 메모리 부족, 드라이버 오류 등으로 멈출 수 있다. 그래서 **경보 출력과 감시는 리눅스와 독립된 MCU**에 맡긴다.

> `report/hardware.md`에서는 RV1106 칩 **안의** 작은 RISC-V 코어가 부저를 맡는 안이었다. 같은 칩 안에 있으면 칩 전원·클럭·메모리 문제가 생길 때 함께 멈출 수 있어서, 이번에 **칩 밖의 독립 MCU**로 바꿨다. (변경 내용은 7장)

## 3. SBC 선정

### 3-1. 맘캠이 SBC에 요구하는 조건

| 조건 | 이유 (근거 문서) |
|---|---|
| ① Rockchip NPU (RKNN) | 추론 엔진 보고서에서 ONNX → RKNN 경로로 결정했다. 양산 칩(RV1106)과 같은 도구를 써야 모델을 그대로 옮길 수 있다 |
| ② 자세(pose) 모델 공식 지원 칩 | Rockchip 공식 자세 예제(yolov8_pose)의 지원 칩 목록에 RV1106이 없다. 지원되는 칩에서 먼저 확실히 돌려 봐야 한다 |
| ③ 양산 칩과 비슷한 NPU 성능 | 너무 빠른 보드에서 개발하면 양산 칩에서 초당 5장이 나오는지 알 수 없다 |
| ④ RAM 2GB 이상 + 데비안 계열 리눅스 | 기능별 컨테이너(Docker)를 돌리려면 메모리와 일반 리눅스가 필요하다 |
| ⑤ MIPI CSI 카메라, Wi-Fi | IR 카메라 연결, 앱 알림 |

### 3-2. 후보 비교

◎ 매우 적합 · ○ 적합 · △ 불리 · ✕ 부적합

| 후보 | 칩 / NPU / RAM | ① RKNN | ② pose 공식 지원 | ③ 양산 칩과 성능 비슷 | ④ 컨테이너 | 판정 |
|---|---|:---:|:---:|:---:|:---:|---|
| **Radxa ROCK 3C** | RK3566, Cortex-A55 4코어 최대 1.6GHz / NPU 1 TOPS / 1·2·4GB | ◎ | ◎ (RK3566 지원) | ◎ (RV1106G3도 1 TOPS) | ◎ (4GB) | **선택** |
| Luckfox Pico Ultra W | RV1106G3, Cortex-A7 1.2GHz / NPU 1 TOPS / 256MB, eMMC 8GB, Wi-Fi 6 | ◎ | △ (목록에 없음) | ◎ (양산 칩 그 자체) | ✕ (256MB, Buildroot) | **양산 칩 검증용으로 함께 사용** |
| Raspberry Pi 5 | BCM2712, Cortex-A76 4코어 2.4GHz / NPU 없음 / 1~16GB | ✕ (별도 AI 가속기 필요, 다른 도구) | — | ✕ | ◎ | 제외 |
| RK3588·RK3576 보드 | NPU 6 TOPS급 / 4GB 이상 | ◎ | ◎ | ✕ (너무 빨라 양산 속도 예측 불가) | ◎ | 제외 |

### 3-3. Radxa ROCK 3C를 고른 이유

1. **양산 칩과 같은 도구, 비슷한 성능.** RK3566 NPU는 1 TOPS로 RV1106G3(1 TOPS)과 같은 급이다. 같은 RKNN-Toolkit2로 만든 모델을 쓰므로, ROCK 3C에서 초당 5장이 나오면 양산 칩에서도 가능성이 높다.
2. **자세 모델이 공식 지원된다.** RK3566은 Rockchip 공식 자세 예제의 지원 칩이라, 모델 문제와 칩 문제를 나눠서 볼 수 있다. ROCK 3C에서 되고 RV1106에서 안 되면 원인은 칩 쪽이다.
3. **컨테이너 개발이 가능하다.** 4GB RAM과 데비안 계열 OS(Radxa OS)로 Docker를 돌려, 기능을 나눠 개발·업데이트할 수 있다. (`report/container.md`)
4. **필요한 연결이 다 있다.** MIPI CSI 카메라, Wi-Fi 5/6 + 블루투스 5, 기가비트 이더넷, 40핀 GPIO(UART·I2C)로 IR 카메라와 MCU를 바로 연결한다.
5. **영상 처리 하드웨어.** 8M ISP와 1080p60 H.264/H.265 인코더가 있어 앱 실시간 보기를 CPU 부담 없이 처리한다.

**Raspberry Pi 5를 고르지 않은 이유:** CPU는 가장 빠르지만 NPU가 없다. AI 가속기를 따로 붙이면 다른 회사의 변환 도구를 써야 해서, 양산 칩(Rockchip)으로 옮길 때 모델 변환을 처음부터 다시 해야 한다.

### 3-4. 양산 칩 검증 보드를 하나 더 두는 이유

ROCK 3C는 개발하기 편하지만 양산 칩이 아니다. 그래서 같은 RV1106G3가 들어간 **Luckfox Pico Ultra W**로 다음을 확인한다.

- 자세 모델이 RV1106에서 RKNN으로 변환·실행되는가 (추론 엔진 보고서의 가장 큰 위험)
- 256MB 메모리 안에 영상 모델 + 오디오 모델 + 나머지 프로그램이 들어가는가
- 초당 5장, 감지 후 5초 이내 경보가 가능한가

> **하드웨어 보고서 갱신:** `report/hardware.md`의 RV1106은 NPU 0.5 TOPS(RV1106G2, 128MB)로 적혀 있다. 메모리와 속도 여유를 위해 양산 칩을 **RV1106G3 (NPU 1 TOPS, 256MB)** 로 올린다.

## 4. MCU 선정

### 4-1. MCU가 맡는 일

| 기능 | 내용 | 연결 |
|---|---|---|
| 경보 부저 | SBC의 "엎드림 의심" 명령을 받아 85dB 부저를 울림. 보호자가 버튼을 누르거나 앱에서 확인할 때까지 유지 | PWM → NPN 트랜지스터 |
| SBC 감시 (하트비트) | SBC가 1초마다 "살아 있음" 신호를 보냄. **10초 동안 안 오면** "감시 중단" 경보음 + 빨간 LED, 그래도 안 오면 SBC 재시작 | UART 수신, GPIO → SBC 리셋 |
| 상태 LED | 정상(초록) · Wi-Fi 끊김(노랑) · 경보(빨강 깜빡임) · 감시 중단(빨강) | GPIO |
| 버튼 | 경보 끄기, 길게 눌러 Wi-Fi 등록 모드 | GPIO 인터럽트 |
| 정전·배터리 감시 | 충전 IC의 전원 상실 신호를 받고 배터리 전압을 재서 SBC에 알림, 배터리 부족 경고음 | GPIO, ADC |

**MCU가 하지 않는 일:** 자세 판단은 하지 않는다(AI 연산 불가). MCU의 역할은 "판단 결과를 확실히 소리로 바꾸는 것"과 "판단하는 쪽이 멈췄는지 알아채는 것"이다.

### 4-2. 후보 비교

| 후보 | 특징 | 맘캠에 맞는 점 | 맞지 않는 점 | 판정 |
|---|---|---|---|---|
| **STM32G031K8** | Cortex-M0+ 64MHz, 플래시 64KB, RAM 8KB, 1.7~3.6V, USART 2개 + 저전력 UART, I2C 2개, 타이머 11개(워치독 2개 포함), 12비트 ADC | 필요한 기능만 있고 단순, 워치독 2개, 저전력 모드, 값이 싸고 산업용으로 오래 공급 | 무선 기능 없음 (필요 없음) | **선택** |
| ESP32-C3 | RISC-V 160MHz, Wi-Fi·BLE 내장 | 개발 쉬움, 강의 실습과 비슷 | Wi-Fi는 SBC에 이미 있음. 무선 기능이 있으면 소비 전류와 보안 점검 범위가 늘어남 | 제외 |
| RP2040 | Cortex-M0+ 2코어 133MHz | 빠르고 저렴 | 플래시가 칩 밖에 있어 부품이 늘고, 저전력 대기에 불리 | 제외 |
| ATmega328P (아두이노) | 8비트 AVR | 자료가 많음 | 오래된 설계, 하드웨어 기능이 적음 | 제외 |
| RV1106 내장 RISC-V | SoC 안의 작은 코어 | 부품 추가 없음 | SoC가 멈추면 같이 멈출 수 있음 (독립성 없음) | 제외 (2장) |

### 4-3. STM32G031K8을 고른 이유

1. **단순해서 안 멈춘다.** 운영체제 없이 경보·감시 코드만 돈다. 코드가 작으면 시험하기 쉽고, 시험한 대로 동작한다.
2. **워치독이 2개다.** MCU 자신이 멈추면 내부 워치독이 MCU를 다시 시작한다. "감시하는 쪽도 감시받는" 구조가 된다.
3. **필요한 연결이 딱 맞는다.** SBC와 통신할 UART, 부저용 PWM 타이머, 배터리 전압을 잴 ADC, 버튼·LED용 GPIO가 모두 있다.
4. **전원 범위가 넓고 전력이 적다.** 1.7~3.6V에서 동작해 배터리 정전 상황에서도 3.3V 상시 전원으로 버티고, 저전력 모드(Stop·Standby)로 대기 전력을 줄인다.
5. **개발이 쉽다.** NUCLEO-G031K8 보드에 디버거가 들어 있어 USB 하나로 코드를 올리고 디버깅한다. 양산 때는 같은 칩만 기판에 올린다.

## 5. SBC ↔ MCU 연결

| 신호 | 방향 | 방식 | 내용 |
|---|---|---|---|
| 데이터 | SBC ↔ MCU | **UART 115200bps**, 3.3V | 하트비트, 경보 명령, 버튼·배터리 상태 |
| SBC 리셋 | MCU → SBC | GPIO (오픈 드레인) | 하트비트가 계속 끊기면 SBC를 다시 시작 |
| 경보 확인 | MCU → SBC | UART 메시지 | 버튼으로 경보를 끈 시각을 앱 기록에 남김 |
| 공통 GND | — | — | 두 보드의 GND를 반드시 연결 (강의 원칙) |

**메시지 형식 (예시):** `[시작 0xAA][종류][길이][내용][CRC-8]`

| 종류 | 보내는 쪽 | 뜻 |
|---|---|---|
| `HB` | SBC | 살아 있음 (1초마다, 영상·소리 분석 상태 포함) |
| `ALARM_ON` / `ALARM_OFF` | SBC | 엎드림 의심 경보 시작 / 해제 |
| `BTN` | MCU | 버튼 눌림 (짧게 / 길게) |
| `PWR` | MCU | 정전 발생, 배터리 전압 |

CRC를 붙여 잡음으로 깨진 메시지가 잘못된 경보를 만들지 않게 한다.

## 6. 전원·전류 (대표값)

| 부품 | 전압 | 전류·전력 | 비고 |
|---|---|---|---|
| Radxa ROCK 3C | USB-C 5V | 수 W (NPU·카메라 동작 시 증가) | 시제품에서 실측. Radxa 권장 전원 어댑터 사용 |
| Luckfox Pico Ultra W | 5V (USB-C 또는 PoE) | 약 1W 이하 예상 | 양산 전력의 기준. 실측 필요 |
| STM32G031K8 | 3.3V (1.7~3.6V) | 동작 시 수 mA, 저전력 모드에서는 훨씬 작음 | 배터리 백업 3.3V 상시 전원에 연결 |
| 경보 부저 | 3.3~5V | 약 20~30mA | MCU가 트랜지스터로 구동 |

MCU는 SBC보다 **먼저 켜지고 나중에 꺼지는** 상시 전원에 연결한다. 그래야 SBC가 부팅 중이거나 꺼져 있어도 경보와 감시가 살아 있다.

## 7. 하드웨어 보고서와 달라지는 점

| 항목 | 이전 (`hardware.md`) | 이번 결정 |
|---|---|---|
| 양산 SoC | RV1106 (NPU 0.5 TOPS) | **RV1106G3** (NPU 1 TOPS, 256MB) |
| 경보 부저 구동 | SoC 내부 RISC-V 코어 | **독립 MCU (STM32G031)** |
| 버튼·상태 LED | SoC GPIO | MCU GPIO |
| 정전 감지 | 충전 IC → SoC | 충전 IC → **MCU** → SBC에 알림 |
| 추가 연결 | — | SBC ↔ MCU UART, MCU → SBC 리셋 선 |
